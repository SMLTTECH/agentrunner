# Памятка агенту: как писать тесты YAxUnit (расширение `tests`)

- Актуально на: 2026-09-21 · движок **YAxUnit 25.12**
- Инфраструктура: `Q:\ba\YAxUnit\` — `YAxUnit-25.12.cfe` (движок), `Smoke-25.12.cfe` (дымовые), `test-config.json` (конфиг запуска), `reports\` (результаты)
- Платформа: локально 8.3.24.1691+ (требование движка — от 8.3.10)
- Решение проекта: тесты живут в **отдельном расширении `tests`** (не в расширении движка). Движок обновляется простой заменой .cfe, расширение `tests` — в git.

---

## 1. Где размещать тесты — жёсткие правила

1. Тесты — **только в расширениях**, не в основной конфигурации. Наше расширение — **`tests`** (имя фиксировано, оно прописано в `filter.extensions` конфига запуска).
2. Тестовый набор = **новый (не заимствованный) общий модуль** расширения `tests`. Не модуль объекта, не модуль формы.
3. В каждом тестовом модуле обязательна **экспортная процедура `ИсполняемыеСценарии()`** — движок вызывает её при загрузке. В ней **только регистрация тестов** — не создавать данные и не инициализировать окружение.
4. Тестовые методы — **экспортные**. Тест = строка регистрации в `ИсполняемыеСценарии` + реализация. Незарегистрированный метод не выполнится (в 1С нет рефлексии).
5. У расширения `tests` тоже снять «Безопасный режим» и «Защиту от опасных действий» (как у движка).
6. После правок расширения — сохранить и обновить конфигурацию БД в конфигураторе.

**Именование** (рекомендация документации, один тестовый модуль на один проверяемый):

| Префикс | Объект | Суффикс | Модуль |
|---|---|---|---|
| `ОМ_` | общий модуль | — | общий модуль |
| `Спр_` / `Док_` / `Обр_` / `Отч_` | справочник / документ / обработка / отчёт | `_МО` | модуль объекта |
| `РБ_`/`РН_`/`РР_`/`РС_`, `ПС_` и др. | регистры, планы | `_ММ` (менеджер), `_НЗ` (набор записей) | соответствующий |

Пример: тесты серверного модуля расширения `sp_РаботаСБюджетом` → общий модуль `ОМ_sp_РаботаСБюджетом` в расширении `tests`.

## 2. Скелет тестового модуля (шаблон)

```bsl
// Расширение: tests. Общий модуль: ОМ_sp_РаботаСБюджетом (серверный, не заимствованный)

Процедура ИсполняемыеСценарии() Экспорт
    ЮТТесты
        .ДобавитьСерверныйТест("РасчетКоэффициентаНДС")
        .СПараметрами(100, 122)
        .Тег("smoke")
        .ВТранзакции();          // откат изменений БД после теста
КонецПроцедуры

Процедура РасчетКоэффициентаНДС(База, Ожидание) Экспорт
    Результат = sp_РаботаСБюджетом.РассчитатьКоэффициент(База);
    ЮТест.ОжидаетЧто(Результат)
        .Заполнено()
        .ИмеетТип("Число")
        .Равно(Ожидание);
КонецПроцедуры
```

**Регистрация** (`ЮТТесты`, вызываются цепочкой):

- `ДобавитьТест(ИмяМетода)` — во всех контекстах, где доступен модуль; `ДобавитьСерверныйТест` / `ДобавитьКлиентскийТест` — ограничение контекста;
- `ДобавитьТестовыйНабор(Имя, Теги)` — группировка;
- `.СПараметрами(Знач1, Знач2, ...)` — до 10 сериализуемых параметров (тест вызовется на каждом наборе);
- `.Тег(...)`, `.ВТранзакции()`, `.УдалениеТестовыхДанных()`, `.Перед(...)`/`.После(...)` (обработчики), `.ЗависитОт(Файлы)`, `.Представление(...)`, `.Настроить(...)`.

## 3. Проверки (assertions)

Входная точка — `ЮТест.ОжидаетЧто(<значение>)`, дальше цепочка проверок:

| Метод | Проверка |
|---|---|
| `.Равно(X)` / `.Заполнено()` / `.ИмеетТип("Число, Строка")` | базовые |
| `.Свойство("Путь")` | переход к свойству, в т.ч. вложенному и в таблице: `.Свойство("Товары[0].Товар")` |
| `.ИмеетДлину(N)` | длина коллекции/строки |

Пример проверки документа (из документации):

```bsl
ЮТест.ОжидаетЧто(ДанныеЗаписи)
    .Свойство("Поставщик").Равно(ДанныеОбъекта.Поставщик)
    .Свойство("Товары")
    .ИмеетДлину(1)
    .Свойство("Товары[0].НомерСтроки").Равно(2);
```

Есть также проверки исключений, данных ИБ (регистры/документы), предикаты, сравнение таблиц — см. [Утверждения](https://bia-technologies.github.io/yaxunit/docs/features/assertions/).

## 4. Тестовые данные

Генератор — `ЮТест.Данные()`:

```bsl
Документ = ЮТест.Данные().КонструкторОбъекта(Документы.бит_ФормаВводаБюджета)
    .Установить("Организация", Организация)
    .ФикцияОбязательныхПолей()          // заполнить обязательные поля фикцией
    .ТабличнаяЧасть("Бюджет")
    .ДобавитьСтроку()
    .Установить("Статья", Статья)
    .Фикция("Сумма")                     // случайное значение
    .Провести();

ДатаНачала = ЮТест.Данные().СлучайнаяДата();
ДатаКонца  = ЮТест.Данные().СлучайнаяДатаПосле(ДатаНачала);
Сумма      = ЮТест.Данные().СлучайноеПоложительноеЧисло(100);
```

Ещё есть загрузка из макетов, поиск и удаление тестовых данных — [Тестовые данные](https://bia-technologies.github.io/yaxunit/docs/features/test-data/). Для разовых фикстур из Excel удобнее своя загрузка, как в существующих обработках.

## 5. Мокирование (Мокито)

Подмена вызовов внешних зависимостей (например, `бит_ОбщегоНазначения`) при проверке изолированной логики:

```bsl
Мокито.Обучение(sp_РаботаСБюджетом)
    .Когда("ПолучитьНастройку").Вернуть(ЗначениеНастройки);
// во время теста вызовы ПолучитьНастройку перехватываются и возвращают ЗначениеНастройки
```

Полный API (Обучение / Когда / Вернуть / ВыброситьИсключение / Пропустить / Наблюдение / прекращение): <https://bia-technologies.github.io/yaxunit/api/Мокито>

## 6. Добавить написанный тест в запуск: `Q:\ba\YAxUnit\test-config.json`

Конфиг уже содержит `"extensions": ["tests", "YAxUnit"]` — новые тесты подхватятся сами. Выбор конкретных тестов — через `filter`:

- **Адресный прогон при разработке** — добавить свой модуль в `filter.modules`:

```json
"filter": {
    "extensions": ["tests", "YAxUnit"],
    "modules": ["ОМ_sp_РаботаСБюджетом"],
    ...
}
```

- **Один тест** — `"tests": ["ОМ_sp_РаботаСБюджетом.РасчетКоэффициентаНДС"]`;
- **По тегу** — `"tags": ["smoke"]`;
- **Полный регресс** — `"modules": []`, `"tests": []`, `"tags": []` (пустые = всё из extensions).

Правило: при разработке — адресный `filter.modules`; перед сдачей — вернуть пустые фильтры и прогнать всё, убедиться, что чужие тесты не сломаны.

## 7. Запуск и результат

Интерактивно (отладка): Предприятие → раздел **YAxUnit → Запуск тестирования**.

Из командной строки (файловая база):

```
"C:\Program Files\1cv8\8.3.24.1691\bin\1cv8c.exe" ENTERPRISE /F "C:\путь\к\базе" /N Администратор /P пароль /C "RunUnitTests=Q:\ba\YAxUnit\test-config.json"
```

(серверная база: `/S Сервер\База`; параметры можно переопределять после `;` — `RunUnitTests=...;showReport=true`).

**Из Git Bash** — обязательно с префиксом, иначе MSYS конвертирует ключи `/F`, `/S`, `/C` в пути и клиент откроет окно выбора базы вместо запуска тестов. Рабочая команда для нашей базы (Windows-аутентификация):

```
MSYS2_ARG_CONV_EXCL="*" MSYS_NO_PATHCONV=1 "C:\Program Files\1cv8\8.3.27.1859\bin\1cv8c.exe" ENTERPRISE /S "10.62.11.48\BitPluse_Dev" /C "RunUnitTests=Q:\ba\YAxUnit\smoke-my.json"
```

Результаты в `Q:\ba\YAxUnit\reports\`: `junit.xml`, `report.json`, `exitcode.txt` (**0 = все тесты зелёные, 1 = есть падения**), лог `tests.log`.

## 8. Дымовые тесты (расширение Smoke)

Готовые автогенерируемые тесты по метаданным базы: код писать не нужно — только настроить и запустить. Расширение `Smoke` уже подключено к тестовой базе (`BitPluse_Dev`).

**Включение.** По умолчанию дымовые тесты ВЫКЛЮЧЕНЫ: без настройки прогон по Smoke даёт 0 тестов и код возврата 0 за секунду (движок при этом работает исправно). Включаются секцией в конфиге запуска:

```json
"ДымовыеТесты": {
    "Использовать": true,
    "ОткрытиеФорм": { "Использовать": true }
}
```

**Виды дымовых тестов** (ключ секции = вид): `ОткрытиеФорм` — открывает формы, ничего не пишет (безопасный); `ЗаписьСправочников`, `ПроведениеДокументов`, `ПроверкаПрав` — создают/записывают данные, выполняются в транзакциях с откатом.

**Дерево настроек и отбор объектов:**

```
ДымовыеТесты → ОткрытиеФорм → <Коллекция> (Справочники, Документы, Отчеты, Обработки, ОбщиеФормы, …) → <Имя объекта>
```

На каждом уровне доступны параметры:

| Параметр | Описание |
|---|---|
| `Использовать` | bool; `false` **гасит ветку целиком** — включённый ниже объект её не оживит |
| `Исключения` | строка/массив шаблонов со `*` по **имени объекта** (`"Классификатор*"`, `"Удалить_*"`); с уровней складываются; заматченный объект пропускается всегда |
| `ОбычныеФормы` / `УправляемыеФормы` | виды форм (в управляемом приложении обычные лучше держать `false`) |
| `<Имя коллекции>` | bool или объект — настройка для всех объектов коллекции |
| `<Имя объекта>` | bool или объект — настройка конкретного объекта (внутри коллекции) |
| `<Имя формы>` | на уровне объекта: отключить конкретную форму (`"ФормаДокумента": false`) |
| `<Вид теста>` | `Новый`, `НоваяГруппа`, `Существующий`, `СуществующаяГруппа`, `Скопированный`, `СкопированнаяГруппа`, `Список`, `Выбор`, `ВыборГруппы`, `Основная`, `Настройки`, `Варианты` — наследуются вниз с переопределением |

Виды тестов по коллекциям: справочники и ПВХ — все виды, включая группы; документы, планы, регистры сведений — `Новый`/`Существующий`/`Скопированный`/`Список`/`Выбор`; регистры накопления/бухгалтерии — `Существующий`/`Список`/`Выбор`; перечисления — `Список`/`Выбор`; отчёты — `Основная`/`Настройки`/`Варианты`; обработки — `Основная`; общие формы — `Общая`. Итоговый список учитывает права текущего пользователя.

**Чёрный список** — отключить лишнее (коллекции, балласт шаблонами, точечно объекты):

```json
"ОткрытиеФорм": {
    "Использовать": true,
    "Перечисления": false,
    "РегистрыСведений": false,
    "Исключения": ["Классификатор*", "Рег*", "Удалить_*"],
    "Документы": { "РеализацияТоваровУслуг": false }
}
```

**Белый список — «только мои объекты»** (основной сценарий для проверки своих доработок): все виды тестов в `false` на уровне `ОткрытиеФорм`, у нужных объектов включить нужные виды:

```json
"ОткрытиеФорм": {
    "Использовать": true,
    "Новый": false, "Существующий": false, "Список": false, "Выбор": false,
    "Скопированный": false, "Основная": false, "Настройки": false, "Варианты": false,
    "ОбычныеФормы": false, "ОбщиеФормы": false,
    "Документы": {
        "бит_ФормаВводаБюджета": { "Существующий": true, "Список": true }
    },
    "Справочники": {
        "бит_СтатьиБюджета": { "Существующий": true, "Список": true }
    }
}
```

**Готовые конфиги** (запуск — той же командой из §7, `filter.extensions: ["Smoke"]` уже прописан):

- `smoke-config.json` — полный прогон по всей конфигурации (БП 3.0 ≈ 7 000 тестов, десятки минут);
- `smoke-my.json` — белый список по бит_*-объектам (править имена под задачу; единицы тестов, минуты).

## 9. Чек-лист агента (от задачи до зелёного прогона)

1. Определить проверяемый модуль и префикс имени (`ОМ_...`/`..._МО`).
2. В расширении `tests` создать общий модуль (не заимствованный), скелет по §2.
3. Подготовить данные через `ЮТест.Данные()` или `.ВТранзакции()`; внешние зависимости отрезать Мокито.
4. Проверки — цепочкой `ЮТест.ОжидаетЧто(...)`; одно логическое утверждение на аспект.
5. Вписать модуль в `filter.modules` конфига (§6), запустить адресно (§7).
6. Убедиться: `exitcode.txt` = 0, тест в `junit.xml` passed. Красный — читать сообщение («Ожидали, что … но это не так»), чинить тест или код.
7. Если правка затрагивает формы объекта (перехваты `ПриСозданииНаСервере`, видимость, команды) — добавить объект в белый список `smoke-my.json` (§8) и прогнать дымовые.
8. Перед сдачей: очистить фильтры, полный прогон, вернуть отчёты.
